情侣飞行棋
一个伪装成飞行棋的双人互动应用

Couples Ludo 起于一个经典飞行棋项目，几轮迭代后已经长成一套七条并行玩法轴的成人向互动应用： 飞行棋仍是入口与主线，剧本杀、沉浸剧场、真心话大冒险、广播剧、节拍器、调教节奏各自成一条完整链路， 小说书房则是藏在密码背后的隐藏世界。全部功能跑在一个无后端、无路由库的纯前端 SPA 里 —— 状态靠 localStorage，音频靠 Cache API，路由靠 App.tsx 里手工 switch。

03

主线机制：飞行棋怎么跑

飞行棋是唯一有完整「配置 → 对局 → 结算 → 复盘」闭环的玩法，也是所有主题包、状态池和个性化逻辑的宿主。

7×7 螺旋棋盘

起点 0（格内数字＝走子顺序）
终点 48（棋盘正中，先到者胜）
普通格 / 幸运 / 陷阱 / 状态格

每局开局随机铺 13 个幸运格、13 个陷阱格、6 个状态格，其余为普通格。 无「出营」规则，棋子沿螺旋线线性前进；越过 48 会反弹（target = 48 - (target - 48)），所以大步数可能把棋子打回后半程。

状态槽与事件判定

  1. 落点 = 48直接判定胜利，结束当前会话并写入历史。
  2. 落点 = 对手格collision 亲密追尾：任务由对手执行，来源是对手选的任务包。
  3. lucky 幸运格任务由对手执行，来源是自己的任务包（幸运＝对手得福利）。
  4. trap 陷阱格任务由自己执行，来源是对手的任务包（陷阱＝自己踩雷）。
  5. status 状态格随机写入 action / condition 槽之一，目标为男或女，来源主题的状态池。
  6. 开局状态对局开始时双方各获得一条 opening 状态，来自 statePools 的 6 条开局池。

P0

阻断级 · 数据丢失与内容错位

编辑内置主题包的用户数据 100% 丢失 useGameState.ts:126-129

normalizeThemes 读档时发现 id 命中内置主题，就用内置定义整个替换掉用户存的那份， 而不是合并。实测复现：对内置主题「暧昧升温」改名 + 手加 3 条 + AI 导入 20 条 → 刷新页面 → 名称回退、任务数从 60 掉回 37，新增内容一条不剩；对照组的自建主题正常保留。

为什么是 P0：README 主推的「自定义主题」与「AI 智能导入」两条能力，对内置主题全部无效， 且无任何提示，用户只会以为是自己操作错了。
修法：内置主题改为以代码版本为基线做合并（保留用户 tasks，只回填代码新增项），或给内置主题加 _edited 标记，标记后不再被默认值覆盖。

普通模式强制注入成人状态 useGameState.ts:372-373 · statePools.ts:54-78

startGame() 无条件调用 buildOpeningStatus('male'/'female')，开局就给双方各挂一条「开局热身」成人状态； 踩状态格时又落到 DEFAULT_ACTION_STATES / DEFAULT_CONDITION_STATES 这两个全局成人池。 statusLogic.ts 与 statePools.ts 里 grep mode 零命中 —— 状态系统完全没有模式概念。

为什么是 P0：普通模式自己的 5 个题库（趣味挑战 / 表演达人 / 脑洞大开…）任务文案完全干净， 说明它本就是给朋友局、聚会局设计的；但状态面板会把「隔着裤子摸自己阴茎」这类文案常驻显示在屏幕上。 这是产品定位与内容审核的双重事故，且用户无法关闭。
修法：状态池按 mode 分片（couple 一套、normal 一套或置空），buildOpeningStatus / buildStatus 接收 mode 参数， 普通模式不挂开局状态、状态格改为空操作。

门禁密码明文写在公开仓库里 VerificationGate.tsx:10,13-14

情侣 1314、普通 1234、小说暗号 9527 全部硬编码在源码常量里， 而 remote 指向 GitHub 公开仓库 tablilixian/couple-flying-chess。任何拿到仓库的人一眼就能看到全部入口口令。

为什么是 P0：这个应用的内容是成人向的，口令门是唯一的准入控制。口令公开等于没有控制， 而线上部署的正是这份仓库的构建产物。
修法：口令改为部署时由环境变量注入构建，或首次进入时强制用户设置；至少移除默认值， 强制首次使用自定义，并轮换线上已公开的三个口令。

P1

功能性 · 跨玩法干扰与数据不可达

剧本引擎的定时器没登记 → 离开剧本后语音还在别的页面响

useScriptEngine.ts:291 和 :303 用 window.setTimeout 直接排下一步，没有存进 timerRef/autoRef， 卸载时的 clearTimers()（:283）清不到。走到 timer/counter 步骤结束的瞬间返回大厅，600ms 后照样 advanceStep() → 朗读台词。 与 eefca69 修过的是同一类 bug，只是发生在剧本页。

广播剧离开页面后音频继续播

RadioPlayerView.tsx:205-211 的卸载清理只 revoke 了 Blob URL，没有 audio.pause()； <audio> 在 :539。按 HTML 规范，媒体元素移出文档后播放不会自动停止， 于是声音在后台继续，而界面上的控制入口已经消失。

广播剧切章节的异步请求没有失效保护 → 幽灵播放 + Blob URL 永久泄漏

RadioPlayerView.tsx:121-194 这个 effect 没有 return 清理函数，卸载时也没递增 playTokenRef。 点「下一章」后立刻返回，IndexedDB 读取 resolve → :165-167 赋了新 Blob URL → :171-174 因 shouldPlayRef 仍为 true 而自行 play()， 该 Blob URL 永远不会被 revoke。

主题包「契约情侣」是死数据

src/data/themes/coupleContractLovers.ts 定义完整（43 条任务 + 状态池），但 themes/index.ts 没有 import 它， 全仓库仅命中文件自身。这批内容永远进不了运行时，UI 里也看不到该主题。

结局数量标称与实际数据不符

coffeeShop 的 endings = 2，但 Script 类型只有一组 endingTitle / endingDesc / endingIcon， ScriptSelectView 只把它当展示数字。列表页向玩家暗示「2 个结局」，实际只有 1 个。
